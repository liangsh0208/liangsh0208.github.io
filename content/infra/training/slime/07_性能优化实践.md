## 1. 概述

本文档汇总 Slime 训练框架各模块的**性能优化策略**，提供系统性的调优指南。内容涵盖**显存优化、计算加速、通信优化、调度优化**等方面，帮助用户在实际训练场景中获得最佳性能。

**优化原则【重点】**：
1. **先诊断后优化**：确定瓶颈所在（计算/通信/显存/数据）
2. **渐进式调优**：一次只改一个参数，观察影响
3. **监控全覆盖**：GPU利用率、显存占用、通信时间、数据等待时间

## 3. 显存优化

### 3.1 显存占用分析

```
┌─────────────────────────────────────────────────────────────────┐
│                    GPU 显存占用分布                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  总显存 = 模型参数 + 梯度 + 优化器状态 + 激活 + KV Cache        │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 模型参数      │ 约 2-4 bytes/param (BF16)              │   │
│  │ (Weights)     │ 7B 模型 ≈ 14 GB                         │   │
│  ├─────────────────────────────────────────────────────────┤   │
│  │ 梯度         │ 与参数同大小                             │   │
│  │ (Gradients)   │ 7B 模型 ≈ 14 GB                         │   │
│  ├─────────────────────────────────────────────────────────┤   │
│  │ 优化器状态    │ Adam: 2x 参数大小                       │   │
│  │ (Optimizer)   │ 7B 模型 ≈ 28 GB (FP32)                  │   │
│  ├─────────────────────────────────────────────────────────┤   │
│  │ 激活         │ 取决于序列长度和 batch size              │   │
│  │ (Activations) │ 长序列场景是主要瓶颈                    │   │
│  ├─────────────────────────────────────────────────────────┤   │
│  │ KV Cache      │ 推理阶段占用，与序列长度成正比          │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 激活重计算 (Activation Recomputation)

```bash
# 完全重计算（最大节省，最慢）
--recompute-granularity full
--recompute-method uniform

# 选择性重计算（推荐）
--recompute-granularity selective
--recompute-num-layers 32  # 指定重计算层数
```

**显存-计算权衡**：

| 策略 | 显存节省 | 额外计算 | 适用场景 |
|-----|---------|---------|---------|
| `full` | ~70% | +33% | 极端显存受限 |
| `selective` | ~50% | +15% | 推荐 |
| `none` | 0% | 0% | 显存充裕 |

### 3.3 GPU Offload 策略

```bash
# 训练模型 Offload（训练间隙）
--offload-train

# Rollout 引擎 Offload（推理间隙）
--offload-rollout

# 组合使用（共享 GPU 场景）
--colocate
--offload-rollout
--offload-train
```

**Offload 流程**：

```
┌─────────────────────────────────────────────────────────────────┐
│                    Offload 时序优化                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  时间线 →                                                       │
│                                                                 │
│  [Rollout 生成]  → [Offload Rollout] → [训练 Actor] → [Offload Actor] │
│       │                  ↓              ↓              ↓        │
│   KV Cache       KV→CPU 显存释放    参数→GPU     参数→CPU        │
│   在 GPU                                         显存释放        │
│                                                                 │
│  关键：训练和推理的显存峰值错开                                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 4. 计算优化

### 4.1 动态批次大小

```bash
# 启用动态批次
--use-dynamic-batch-size
--max-tokens-per-gpu 32768  # 每个 GPU 的 token 上限
```

**原理**：根据各样本的序列长度动态调整每个微批次的样本数，使每个 GPU 的计算量趋于均匀。

```
┌─────────────────────────────────────────────────────────────────┐
│                    动态批次 vs 固定批次                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  固定批次 (micro_batch_size=4):                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ GPU0: [短,短,短,短] = 4K tokens   ████████░░░░ 32%     │   │
│  │ GPU1: [长,长,长,长] = 16K tokens  ████████████████ 100% │   │
│  │ GPU2: [中,中,中,中] = 8K tokens   ████████████ 62%      │   │
│  └─────────────────────────────────────────────────────────┘   │
│  问题：GPU 利用率不均，存在气泡                                  │
│                                                                 │
│  动态批次 (max_tokens=16K):                                     │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ GPU0: [短,短,短,短,短,短,短,短] = 8K tokens  ████████   │   │
│  │ GPU1: [长,长] = 16K tokens                   ████████   │   │
│  │ GPU2: [中,中,中,中] = 8K tokens              ████████   │   │
│  └─────────────────────────────────────────────────────────┘   │
│  优势：各 GPU token 数接近，计算负载均衡                        │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 5. 通信优化

### 5.1 并行策略选择

```
┌─────────────────────────────────────────────────────────────────┐
│                    并行策略决策树                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  GPU 数量 < 8:                                                  │
│  └─> TP=8, PP=1, DP=1                                          │
│                                                                 │
│  GPU 数量 < 32:                                                 │
│  └─> TP=8, PP=4, DP=1                                          │
│                                                                 │
│  GPU 数量 < 128:                                                │
│  └─> TP=8, PP=4, DP=4                                          │
│                                                                 │
│  GPU 数量 >= 128:                                               │
│  └─> TP=8, PP=8, DP=8 + CP=4 或 EP=8                          │
│                                                                 │
│  原则：                                                         │
│  1. TP 组尽量在同一节点（减少跨节点通信）                        │
│  2. PP 用于扩展层数，DP 用于扩展数据                             │
│  3. CP 用于长序列，EP 用于 MoE                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 通信重叠

## 8. 问题排查

### 8.1 OOM (Out of Memory)

```
诊断流程：
1. 确认哪个阶段 OOM：
   - 模型加载：--tensor-model-parallel-size 加大
   - Rollout：--rollout-tp-size 加大
   - 训练：--micro-batch-size 减小

2. 检查显存分布：
   nvidia-smi --query-gpu=memory.used,memory.total --format=csv -l 1

3. 解决方案：
   - 减小 micro-batch-size
   - 启用激活重计算
   - 使用 CP 分担长序列
   - Offload 非活跃模型
```

### 8.2 训练速度慢

```
诊断流程：
1. 检查 GPU 利用率：
   nvidia-smi dmon -s u

2. 可能原因：
   - 数据加载瓶颈：CPU→GPU 带宽不足
   - 通信瓶颈：跨节点 IB 带宽不足
   - 计算气泡：批次不均衡

3. 解决方案：
   - 启用动态批次
   - 启用通信重叠
   - 增加 Rollout 并行度
   - 使用 Transformer Engine
```

### 8.3 NCCL 通信错误

```
诊断流程：
1. 启用 NCCL 日志：
   export NCCL_DEBUG=INFO
   export NCCL_DEBUG_SUBSYS=ALL

2. 常见错误：
   - NCCL WARN Cuda failure：GPU 通信问题
   - NCCL WARN Call to connect returned -1：端口冲突

3. 解决方案：
   - 检查 IB 网络：ibstat
   - 检查 NCCL 版本：python -c "import torch; print(torch.cuda.nccl.version())"
   - 尝试强制 P2P：export NCCL_P2P_LEVEL=5
```

### 8.4 数值异常 (NaN/Inf)

```
诊断流程：
1. 启用检查：
   --check-for-nan-in-loss-and-grad

2. 可能原因：
   - 梯度爆炸
   - 学习率过大
   - 混合精度溢出

3. 解决方案：
   - 启用梯度裁剪：--clip-grad 1.0
   - 降低学习率
   - 启用 FP32 注意力：--attention-softmax-in-fp32
   - 启用 FP32 梯度累积：--accumulate-allreduce-grads-in-fp32
```

### 8.5 Checkpoint 加载慢

```
诊断流程：
1. 检查 checkpoint 大小和数量
2. 检查存储 I/O：iostat -x 1

解决方案：
- 使用 SSD/NVMe 存储
- 增加并行读取
- 使用分布式 checkpoint 格式
- 跳过优化器状态（仅推理）：skip_load_optimizer=True
```

## 10. 诊断与调试工具集

Slime 在 `slime/utils/` 下内置了多套诊断与调试工具，覆盖性能剖析、分布式追踪、数值调试、训练状态导出等场景。本节逐一介绍其核心功能与使用方式。

### 10.1 性能剖析 (profile_utils.py)

`TrainProfiler` 封装了 PyTorch Profiler 和内存 Profiler，支持在训练不同阶段自动采集性能数据。

**使用方式**：
```bash
# 启用 PyTorch Profiler（在指定区间采集）
--use-pytorch-profiler
--profile-target train_overall,train_actor,train_log_probs
--profile-step-start 10
--profile-step-end 20

# 启用 Torch 内存快照（OOM 时自动 dump）
--record-memory-history
--memory-recorder torch
--memory-snapshot-dir ./memory_dumps
--memory-snapshot-num-steps 15

# 或使用 memray 进行 Python 级内存追踪
--memory-recorder memray
--memory-snapshot-num-steps 10
```

**关键设计**：
- `train_overall`：覆盖整个训练生命周期，输出到 TensorBoard
- `train_actor / train_log_probs`：仅覆盖对应迭代区间，用于定位具体阶段的热点
- Torch 内存 Profiler 注册了 `torch._C._cuda_attach_out_of_memory_observer`，在 OOM 时自动 dump 堆栈和内存快照

### 10.2 分布式追踪 (trace_utils.py)

Slime 自带的分布式追踪系统，用于记录单个 sample 从 Rollout 到训练完成的完整生命周期事件，支持跨 Actor/Rollout/Ray 节点传递 trace 上下文。

**核心概念**：
- `TraceHandle`：追踪句柄，包含 `trace_id`, `carrier`（事件列表）, `sample_id`, `group_id`
- `trace_span`：上下文管理器，自动记录 span 的开始和结束，支持嵌套
- `trace_event`：记录离散事件，如 "rollout_start", "reward_computed"
- `trace_function`：装饰器，自动为函数调用创建 span

**使用示例**：
```python
from slime.utils.trace_utils import trace_span, trace_event

# 在 Rollout 阶段绑定 trace
handle = bind_trace(sample)

# 记录事件
trace_event(handle, "rollout_start", attrs={"engine": "sglang"})

# 使用 span 包裹代码块
with trace_span(handle, "reward_computation") as span:
    reward = compute_reward(sample)
    span.set("reward", reward)
```

**场景**：精确定位**长延迟 sample** 的瓶颈在哪个阶段（Rollout？Reward？还是训练拼接？）。

### 10.3 训练调试导出 (train_dump_utils.py)

`save_debug_train_data` 用于在指定 rollout step 将训练数据（包括 rollout 输出、loss mask、logits 等）导出为 `.pt` 文件，便于离线复现和调试。

```bash

```

导出的数据可在本地脚本中加载：
```python

```

### 10.4 张量备份与对比 (tensor_backper.py)

`TensorBackuper` 提供两种工作模式，用于训练中的数值一致性校验：

| 模式 | 类 | 行为 | 显存/存储开销 |
|-----|-----|------|------------|
| Normal | `_TensorBackuperNormal` | 将参数量化备份到 CPU pinned memory，支持多 tag、恢复 | 高（全量备份） |
| Noop | `_TensorBackuperNoop` | 仅计算参数 hash，用于校验参数是否被意外修改 | 极低 |

**典型用法**：在 Weight Streaming（在线权重同步）或 Offload/Restore 流程前后备份张量，确保同步/恢复后的参数与预期一致。

```python
backuper = TensorBackuper.create(source_getter=lambda: model.named_parameters(), single_tag=None)
backuper.backup("before_sync")
# ... 执行权重同步 ...
backuper.restore("before_sync")  # 若需要回滚
```

### 10.5 MoE 路由录制与重放 (routing_replay.py)

用于**确定性复现 MoE 路由行为**，或**对比不同策略下路由分布的变化**。通过 monkey-patch `compute_topk` 实现无侵入式录制。

**工作流**：
```bash
# 1. 录制阶段：保存每一步的 top_indices
ENABLE_ROUTING_REPLAY=1 ROUTING_REPLAY_STAGE=record python train.py ...

# 2. 重放阶段：用录制的路由执行 forward（忽略当前门控输出）
ENABLE_ROUTING_REPLAY=1 ROUTING_REPLAY_STAGE=replay_forward python train.py ...

# 3. 反向重放：用录制的路由执行 backward
ENABLE_ROUTING_REPLAY=1 ROUTING_REPLAY_STAGE=replay_backward python train.py ...

# 4. fallthrough：不录制也不重放，直接透传
ROUTING_REPLAY_STAGE=fallthrough
```

**用途**：
- 验证 MoE 负载均衡策略的稳定性
- 分离路由变化对训练动态的影响（固定路由，只训练专家权重）

### 10.6 FLOPs 计算 (flops_utils.py)

提供精细到模块级别的 FLOPs 估算，支持 Dense 和 MoE 模型：

```python
from slime.utils.flops_utils import calculate_fwd_flops

total_flops = calculate_fwd_flops(seqlens=[1024, 2048], args=model_args)
# 返回：embedding + qkv_proj + attention + output + mlp + lm_head 的总 FLOPs
```

**支持的模块**：
- `calculate_embedding_flops`
- `calculate_qkv_projection_flops`（支持 MLA：q_lora_rank / kv_lora_rank）
- `calculate_attention_flops`（支持 qk_pos_emb_head_dim / v_head_dim）
- `calculate_mlp_flops`（支持 MoE：moe_ffn_hidden_size * topk + shared_expert）

### 10.7 Loss Mask 生成 (mask_utils.py)

`MultiTurnLossMaskGenerator` 为 Qwen/Qwen3/Qwen3.5 系列模型生成多轮对话的 loss mask，支持工具调用、system message 和多模态对齐。

```python
from slime.utils.mask_utils import MultiTurnLossMaskGenerator

gen = MultiTurnLossMaskGenerator(tokenizer, tokenizer_type="qwen3_5")
token_ids, loss_mask = gen.get_loss_mask(messages)
```

**特性**：
- Qwen3.5 通过 `offset_mapping` 实现字符级 mask 生成，精准控制 think / answer 段落
- `get_loss_mask_with_multimodal_alignment`：处理多模态输入时 tokenizer 和 processor 的 token 数不一致问题
- `get_response_lengths`：从 loss mask 中计算 response 长度

### 10.8 异步执行工具 (async_utils.py)

在 Ray / Megatron 的同步训练主循环中，部分 I/O 操作（如 Checkpoint 保存、日志上传）需要异步执行以避免阻塞 GPU 计算。

```python
from slime.utils.async_utils import run

# 在同步代码中执行异步函数
run(async_upload_checkpoint(path))
```

底层维护一个全局的后台 `asyncio` 事件循环线程，`run(coro)` 会阻塞等待协程完成，但不会阻塞主线程的其他工作（注意：当前实现是同步阻塞的，需配合 `asyncio.create_task` 使用才能真正异步）。

### 11.3 训练速度诊断流程

```bash
# 诊断脚本：profile_rollout.sh

# Step 1: 测量纯 Rollout 速度 (无训练)
python train.py \
    --debug-rollout-only \
    --profile-rollout \
    --num-rollout 3
# 分析：若 Rollout 时间 >> 训练时间，则瓶颈在生成
# 优化：增加 Rollout GPU、优化 SGLang 参数、增大 --rollout-max-num-seqs

# Step 2: 测量纯训练速度 (无 Rollout)
python train.py \
    --debug-train-only \
    --profile-train \
    --num-rollout 3
# 分析：若训练时间 > 3x 理论计算时间，则瓶颈在并行效率
# 优化：调整 TP/PP 配比、减少通信、启用 AC

# Step 3: 启用详细计时
--log-timers-to-tensorboard \
--log-interval 1
# 在 TensorBoard 查看 time/rollout, time/train 分布
```
