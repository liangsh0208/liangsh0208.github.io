# Fire-Flyer File System（3FS）项目总览

> 源码仓库：`deepseek-ai/3FS`  
> 主要语言：C++17（核心服务）、Rust（Chunk Engine）、Python（部署工具）  
> 核心依赖：FoundationDB、RDMA (InfiniBand/RoCE)、Folly、RocksDB

---

## 1. 项目定位

3FS（Fire-Flyer File System）是 DeepSeek 专为 AI 训练与推理负载设计的**高性能分布式文件系统**。与 Lustre、HDFS 等传统分布式文件系统不同，3FS 的设计目标直接面向大规模 AI 工作负载：

- **AI 训练数据加载**：支持对大型数据集的随机访问，无需预取或数据 shuffle。
- **检查点（Checkpoint）**：高吞吐量并行写入，支持大规模分布式训练的模型保存。
- **KV 缓存（KVCache）**：为 LLM 推理提供低成本、高吞吐的替代 DRAM 缓存方案。
- **数据分析（Data Analytics）**：支持 GraySort 等大规模数据洗牌与排序任务。

核心性能指标（生产环境数据）：
| 场景 | 性能 |
|------|------|
| 180 节点集群峰值读吞吐 | **6.6 TiB/s** |
| GraySort（110.5 TiB / 50 计算节点） | **3.66 TiB/min** |
| KVCache 峰值读吞吐（单集群） | **40 GiB/s** |

## 2. 核心设计理念

### 2.1 解耦架构（Disaggregated Architecture）
计算与存储节点完全分离。应用程序以**无感知本地性（Locality-Oblivious）**的方式访问存储，任意客户端节点可访问集群中任意存储节点上的数据，存储资源对上层完全透明。

### 2.2 强一致性
采用 **CRAQ（Chain Replication with Apportioned Queries）** 协议实现强一致性。写入必须经过链中所有副本，读取可从链中任意副本读取（均匀分摊读流量），在全闪存场景下充分发挥 SSD 和 RDMA 网络的带宽。

### 2.3 标准文件接口
底层使用 FoundationDB 维护元数据，对外提供标准 POSIX 文件系统接口：
- 原子目录操作（rename、递归删除）
- 硬链接与软链接
- 熟悉的文件 API，无需学习新的存储接口

### 2.4 异步零拷贝 I/O（USRBIO）
针对 FUSE 性能限制（内存拷贝开销、锁竞争），设计了原生的**异步零拷贝 API**（User Space Ring Based IO），灵感来源于 Linux io_uring：
- **Iov（IO Vector）**：用户进程与 FUSE 守护进程共享的大型内存区域，RDMA 内存注册由客户端统一管理。
- **Ior（IO Ring）**：小型共享环形缓冲区，类似 io_uring 的 SQE/CQE 机制，用于提交 I/O 请求和获取完成事件。

## 4. 四大核心组件

### 4.1 集群管理器（Mgmtd）
- 通过心跳机制进行故障检测，维护存储目标的公共状态和本地状态。
- 维护全局链表（Chain Table），管理 CRAQ 副本链的版本和成员变更。
- 将集群配置分发给所有服务和客户端。
- 支持多实例部署，通过 Primary 选举实现高可用。

### 4.2 元数据服务（Meta）
- **无状态设计**：元数据完全持久化到 FoundationDB，服务本身不保存状态。
- 实现完整的文件系统语义：create、open、rename、symlink、hardlink、list 等。
- 文件 Inode 使用 `INOD` 前缀 + inode_id（小端编码）作为 FoundationDB key，实现数据分散分布。
- 目录项使用 `DENT` 前缀 + 父 inode_id + 名称，支持高效范围查询实现目录列举。

### 4.3 存储服务（Storage）
- 每个存储节点管理多块 SSD，提供 Chunk Store 接口。
- 实现 CRAQ 协议：写请求从链头（Head）出发向后传播，读请求可在任意链节点完成。
- 底层使用 **Chunk Engine**（Rust 实现）管理物理存储，支持 COW 语义和原子提交。
- 提供 AIO/io_uring 读取加速，通过 RDMA 直接读写数据到客户端内存（零拷贝）。

### 4.4 客户端（Client）
- **FUSE 客户端**：低门槛，兼容所有应用，但受 FUSE 内核限制（内存拷贝、锁竞争）。
- **Native 客户端（USRBIO）**：高性能，零拷贝，基于共享内存环形缓冲区的异步 I/O。
- 客户端在 `open()` 时从 Meta 服务获取文件布局信息，之后独立计算 Chunk ID 和链位置，最小化 Meta 服务在关键路径上的参与。

## 7. 技术栈总结

| 层次 | 技术选型 | 选择原因 |
|------|----------|---------|
| 语言 | C++17 (核心), Rust (ChunkEngine) | C++ 生态成熟；Rust 保证内存安全且性能优异 |
| 协程 | Folly Coroutines (CoTask/CoTryTask) | 统一异步编程模型，避免回调地狱 |
| 序列化 | 自研 Serde（基于反射宏） | 零开销序列化，支持 JSON 可读格式 |
| 网络 | RDMA (InfiniBand/RoCE) + TCP | RDMA 用于数据传输，TCP 用于控制路径 |
| 元数据存储 | FoundationDB | 事务支持（SSI）、无状态服务架构 |
| 数据存储 | RocksDB (元数据) + 自定义文件 (数据) | RocksDB 负责 chunk 元数据；数据直接落盘 |
| 监控 | ClickHouse + 自研 Monitor Collector | 大规模时序数据存储与分析 |
| 构建 | CMake + Cargo | C++ 与 Rust 混合构建 |
