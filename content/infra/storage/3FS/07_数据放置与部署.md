## 1. 数据放置的核心问题

3FS 将文件数据切分为 Chunk，通过 CRAQ 链式复制分布到多个存储节点。数据放置（Chain Table 的构造）需要满足两个目标：

1. **负载均衡**：正常运行时，读写流量均匀分布到所有存储节点和 SSD。
2. **故障恢复均衡**：单节点故障时，故障流量均匀分散到尽可能多的其他节点，避免少数节点成为瓶颈。

第二个目标是 3FS 数据放置的核心挑战，通过**整数规划（Integer Programming）**求解最优方案。

---

## 2. 数学建模

### 2.1 均衡故障恢复（Balanced Incomplete Block Design）

设集群有 V 个存储节点，副本数为 K，每块 SSD 创建 R 个 Storage Target，数据放置问题转化为：

**目标**：构造 Chain Table，使得任意节点故障时，故障流量均匀分散到所有其他节点。

**形式化**：对任意两个节点 i 和 j（i ≠ j），它们在同一条链中共同出现的次数 λ(i,j) 应尽量相等。

```python
# deploy/data_placement/src/model/data_placement.py
# 使用 Pyomo 建模，HiGHS 求解器求解

# 决策变量：x[chain, position, node] ∈ {0, 1}
#   表示节点 node 是否在 chain 的第 position 个位置

# 约束：
# 1. 每条链有 K 个不同节点
# 2. 每个节点恰好出现在相同数量的链中
# 3. 任意两个节点在同一链中的共现次数 λ(i,j) ∈ [lb, ub]（尽量接近）

# 目标函数：最小化 max(λ(i,j)) - min(λ(i,j))
```

**实际求解示例**（5 节点，3 副本）：

```bash
python src/model/data_placement.py \
    -ql -relax -type CR \
    --num_nodes 5 \
    --replication_factor 3 \
    --min_targets_per_disk 6 \
    --init_timelimit 600

# 最优解验证输出：
# min_peer_traffic=1.5  max_peer_traffic=1.5
# total_traffic=30.0  max_total_traffic=30
# → 任意两个节点的共现次数完全相等（1.5，即每对节点共享 1.5 个链/目标）
```

当 `min_peer_traffic == max_peer_traffic` 时，说明找到了完美的均衡方案。

### 2.2 为什么均衡故障恢复很重要

不均衡方案的问题（示意）：

```
不均衡：节点 A 与 B、C 相邻（但 A 不与 D、E、F 相邻）
→ A 故障时，100% 流量压到 B 和 C
→ B、C 立即过载，成为新瓶颈

均衡：节点 A 与所有其他节点都相邻
→ A 故障时，流量均匀分散到 B、C、D、E、F（各 20%）
→ 系统总吞吐量几乎不受影响
```

## 3. 链表生成流程

```bash
# 第一步：求解整数规划，生成关联矩阵
python src/model/data_placement.py \
    -ql -relax -type CR \
    --num_nodes 5 --replication_factor 3 \
    --min_targets_per_disk 6

# 输出：output/DataPlacementModel-v_5-b_10-r_6-k_3-λ_2-lb_1-ub_1/
#       incidence_matrix.pickle

# 第二步：根据关联矩阵生成 Chain Table
python src/setup/gen_chain_table.py \
    --chain_table_type CR \
    --node_id_begin 10001 --node_id_end 10005 \
    --num_disks_per_node 16 \
    --num_targets_per_disk 6 \
    --incidence_matrix_path output/.../incidence_matrix.pickle

# 生成文件：
# generated_chain_table.csv  ← 链表定义
# generated_chains.csv       ← 每条链的目标列表
# create_target_cmd.txt      ← 创建 Storage Target 的 admin_cli 命令
# remove_target_cmd.txt      ← 删除命令（用于回滚）
```

## 4. 系统部署架构

### 4.1 标准六节点部署

```
┌─────────────────────────────────────────────────────────────┐
│ 节点类型    │ 服务                │ 说明                      │
├─────────────┼─────────────────────┼──────────────────────────┤
│ meta 节点   │ mgmtd_main         │ 集群管理，NodeID=1        │
│             │ meta_main          │ 元数据服务，NodeID=100    │
│             │ monitor_collector  │ 监控数据收集              │
│             │ FoundationDB       │ 分布式 KV 存储（元数据）  │
│             │ ClickHouse         │ 监控时序数据存储          │
├─────────────┼─────────────────────┼──────────────────────────┤
│ storage1~5  │ storage_main       │ 存储服务，NodeID=10001~5  │
│             │                    │ 各节点 16 块 14TB SSD     │
│             │                    │ 2×200Gbps InfiniBand NIC  │
└─────────────┴─────────────────────┴──────────────────────────┘
```

### 4.2 配置文件体系

每个服务使用三层配置文件：

```
mgmtd_main_launcher.toml   ← 启动配置（cluster_id, FDB 连接）
mgmtd_main_app.toml        ← 应用配置（node_id, 网络地址）
mgmtd_main.toml            ← 服务运行配置（热更新支持）
```

服务配置支持**热更新（Hot Reload）**：标注 `CONFIG_HOT_UPDATED_ITEM` 的配置项可以通过 `admin_cli setConfig` 在不重启服务的情况下更新。

## 5. 部署步骤详解

### 5.1 集群初始化

```bash
# 初始化集群（只需执行一次）
/opt/3fs/bin/admin_cli -cfg /opt/3fs/etc/admin_cli.toml \
    "init-cluster --mgmtd /opt/3fs/etc/mgmtd_main.toml 1 1048576 16"
# 参数说明：
# 1        → chain_table_id
# 1048576  → chunk_size（1MB）
# 16       → stripe_size
```

### 5.2 存储目标管理

```bash
# 创建 Storage Target（每个 SSD 分区上创建多个 Target）
/opt/3fs/bin/admin_cli "create-target --node 10001 --disk /dev/nvme0n1p1 --target 1"

# 按 gen_chain_table.py 生成的命令批量创建所有 Target
cat create_target_cmd.txt | /opt/3fs/bin/admin_cli
```

### 5.3 链表设置

```bash
# 导入生成的链表（将 generated_chain_table.csv 转为 admin_cli 命令）
/opt/3fs/bin/admin_cli "set-chain-table --table-id 1 --csv generated_chain_table.csv"
```

### 5.4 FUSE 挂载

```bash
# 挂载 3FS 文件系统
/opt/3fs/bin/hf3fs_fuse_main \
    -cfg /opt/3fs/etc/hf3fs_fuse_main.toml \
    --mountpoint /mnt/3fs \
    --allow_other
```

## 6. 序列化框架（Serde）

3FS 自研了一套基于 C++ 反射宏的序列化框架，用于所有 RPC 消息、配置和元数据的序列化：

```cpp
// src/common/serde/Serde.h
// 声明一个可序列化的结构体字段
#define SERDE_STRUCT_FIELD(NAME, DEFAULT, ...)
#define SERDE_CLASS_FIELD(NAME, DEFAULT, ...)

// 示例：
struct RoutingInfo {
  SERDE_STRUCT_FIELD(routingInfoVersion, RoutingInfoVersion(0));
  SERDE_STRUCT_FIELD(nodes, NodeMap{});
  SERDE_STRUCT_FIELD(chains, ChainMap{});
};
```

**序列化特点：**
- **二进制格式**（默认）：基于 `DownwardBytes` 的高效二进制序列化，用于网络传输。
- **JSON 格式**（调试）：同一套宏同时生成 JSON 序列化代码，用于日志和调试。
- **配置文件**（TOML）：配置系统使用相同的反射机制，支持 TOML 格式读取。
- **热更新**：`CONFIG_HOT_UPDATED_ITEM` 标注的字段变更时自动触发回调。

## 7. 监控体系

### 7.1 指标收集

所有服务通过 `Monitor Collector` 汇聚指标，存储到 **ClickHouse** 时序数据库：

```toml
# monitor_collector_main.toml
[server.monitor_collector.reporter]
type = 'clickhouse'
[server.monitor_collector.reporter.clickhouse]
db = '3fs'
host = '<CH_HOST>'
port = '<CH_PORT>'
```

### 7.2 关键指标

`docs/metrics.md` 中定义了系统的核心监控维度：

| 指标类别 | 内容 |
|---------|------|
| Storage 吞吐 | 读/写字节数、IOPS、RDMA 延迟 |
| Chain 状态 | serving/syncing/waiting 目标数量 |
| Meta 操作 | 每种操作的 QPS、P99 延迟、FDB 事务冲突率 |
| Mgmtd | 心跳次数、路由版本、链版本变更 |
| Client | IoRing 使用率、Iov 注册数量、读写吞吐 |

## 8. 构建系统

### 8.1 C++ 部分（CMake）

```cmake
# CMakeLists.txt（顶层）
cmake_minimum_required(VERSION 3.20)
project(hf3fs)

# 关键编译选项
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_COMPILER clang++-14)

# SHUFFLE_METHOD 控制 std::shuffle 实现（不同编译器版本兼容性）
# -DSHUFFLE_METHOD=g++10 或 -DSHUFFLE_METHOD=g++11
# 已部署集群必须使用固定值，否则 Chunk 寻址会因洗牌结果不同而出错
```

**重要说明**：`SHUFFLE_METHOD` 参数锁定了 `std::shuffle` 的具体实现。g++10 和 g++11 使用不同的随机数生成算法，同一 `seed` 会产生不同的 Chain 排列，导致客户端和服务端计算的 Chunk 位置不一致。新集群选定后必须固定此参数。

### 8.2 Rust 部分（Cargo）

```toml
# src/storage/chunk_engine/Cargo.toml
[package]
name = "chunk-engine"
version = "0.1.0"
edition = "2021"

[dependencies]
cxx = "1"           # C++/Rust FFI
rocksdb = { ... }   # RocksDB 绑定
lockmap = { ... }   # 分片锁哈希表（MetaCache）
derse = { ... }     # 轻量级序列化
tinyvec = { ... }   # ETag 小数组优化

[build-dependencies]
cxx-build = "1"     # 生成 C++ 兼容头文件
```

### 8.3 混合构建

```cmake
# CMakeLists.txt 中集成 Rust 构建
add_subdirectory(src/storage/chunk_engine)
# cargo build --release → 生成 libchunk_engine.a
# C++ target 链接 libchunk_engine.a + 自动生成的 cxx 头文件
```
