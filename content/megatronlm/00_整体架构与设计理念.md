## 1. 模块概述

Megatron-LM 是 NVIDIA 开发的大规模分布式训练框架，专为训练千亿甚至万亿参数规模的 Transformer 模型而设计。项目采用模块化架构，将核心并行策略、训练流程、推理引擎和强化学习能力有机整合。

### 1.1 项目定位对比

| 特性 | Megatron-LM | nanotron | DeepSpeed | NeMo |
|------|-------------|----------|-----------|------|
| **定位** | 生产级训练框架 | 教育/轻量框架 | 通用优化器框架 | NVIDIA 官方上层框架 |
| **代码规模** | 500K+ 行 | 50K 行 | 200K+ 行 | 300K+ 行(基于Megatron) |
| **TP实现** | 原生 + 融合内核 | 纯原生实现 | 有限支持 | 继承Megatron |
| **PP实现** | 1F1B/交错式 | 基础1F1B | PipeDream风格 | 继承Megatron |
| **MoE支持** | 原生深度集成 (DeepSeek风格) | 基础支持 | DeepSpeed-MoE | 基于Megatron MoE |
| **RL支持** | 原生GRPO/PPO实现 | 需外部集成 | 需外部集成(TRL) | RLHF支持 |
| **推理优化** | 框架内原生支持 | 无 | 有限 | Triton/FasterTransformer |
| **商业支持** | NVIDIA企业支持 | 社区支持 | 微软支持 | NVIDIA官方支持 |

### 1.3 关键设计决策

| 维度 | 设计决策 | 原理与权衡 |
|------|---------|-----------|
| **并行策略** | 5D并行: TP×PP×DP×CP×EP = WORLD_SIZE | 正交分解各维度，避免通信冲突；TP局限在节点内，PP跨节点通信量小 |
| **配置系统** | 双轨制: arguments.py + TransformerConfig | 命令行参数面向用户，Config对象面向开发者；分工明确 |
| **通信抽象** | Autograd Function封装 | 通信与计算无缝融合，用户无感知；反向传播自动触发正确通信 |
| **MoE架构** | DeepSeek-V3风格: EP+TP+共享专家 | EP跨节点分发token，TP节点内计算；共享专家提升稳定性 |
| **RL架构** | 框架内原生支持GRPO | 避免来回切分模型，显存更高效；通信一体化设计 |

## 3. 核心概念与实现

### 3.1 并行维度计算

**Rank映射公式**（以 `tp-cp-ep-dp-pp` 顺序为例）:

```python
# 文件: megatron/core/parallel_state.py:252

def generate_masked_orthogonal_rank_groups(
    world_size: int,
    parallel_size: List[int],  # [tp_size, cp_size, ep_size, dp_size, pp_size]
    mask: List[bool]           # 选择要生成的并行组维度
) -> List[List[int]]:
    """
    生成正交并行组的算法。
    
    核心公式:
        global_rank = tp_rank 
                    + cp_rank * tp_size 
                    + ep_rank * tp_size * cp_size
                    + dp_rank * tp_size * cp_size * ep_size
                    + pp_rank * tp_size * cp_size * ep_size * dp_size
    
    例如: world_size=16, parallel_size=[2,1,1,4,2], mask=[False,False,False,True,False]
    这将生成DP组: 每个DP组包含2个rank（消除TP/CP/EP/PP维度）
    """
```

**5D并行配置示例**:

```python
# 128 GPU配置示例
world_size = 128
tensor_parallel_size = 2      # 节点内2卡TP
pipeline_parallel_size = 4    # 跨4节点PP
data_parallel_size = 16       # 16组DP
context_parallel_size = 1     # 暂不使用
expert_parallel_size = 2      # MoE专家并行

# 验证: 2 * 1 * 2 * 16 * 4 = 128 (符合WORLD_SIZE)
```

### 3.2 进程组初始化流程

```python
# 文件: megatron/core/parallel_state.py:549

def initialize_model_parallel(
    tensor_model_parallel_size: int = 1,
    pipeline_model_parallel_size: int = 1,
    virtual_pipeline_model_parallel_size: Optional[int] = None,
    context_parallel_size: int = 1,
    expert_model_parallel_size: int = 1,
    order: str = "tp-cp-ep-dp-pp",  # 并行维度顺序，可自定义
    ...
) -> None:
    """
    初始化模型并行进程组的完整流程：
    
    1. 计算各维度大小，验证 WORLD_SIZE 可整除
    2. 根据order确定rank映射规则
    3. 为每个并行维度调用 generate_masked_orthogonal_rank_groups 生成组
    4. 对复合需求(如算子融合)创建组合组(TP+DP, TP+CP等)
    5. 保存所有进程组到全局变量
    """
```

### 3.4 与nanotron对比

| 方面 | Megatron-LM | nanotron |
|------|-------------|----------|
| **并行状态管理** | 全局变量 `_TENSOR_MODEL_PARALLEL_GROUP` 等 | 显式传递 `ParallelContext` 对象 |
| **层定义方式** | `ModuleSpec` 工厂模式，支持TE/本地切换 | 直接子类化 `nn.Module` |
| **配置传递** | 双轨制 (args + config)，较复杂 | 单一配置对象，简洁直接 |
| **通信集成** | Autograd Function封装，无缝 | 显式调用通信函数 |
| **PP调度** | 1F1B + Interleaved + Combined (103KB) | 基础1F1B |
| **MoE支持** | 深度集成，EP/TP/共享专家 | 不支持 |
| **MoE路由** | TopK/Sinkhorn/Expert Choice (73KB) | 不适用 |
| **检查点** | 分布式检查点，跨配置加载 | 简单sharding |

**设计哲学差异**:
- **Megatron**: 生产优先，功能全面，牺牲简洁换性能
- **nanotron**: 教育优先，代码清晰，便于学习核心概念

## 5. 常见问题与排查

### 5.1 初始化问题

**Q: `RuntimeError: WORLD_SIZE (16) not divisible by model parallel size (20)`**

```python
# 原因: 各并行维度乘积不等于WORLD_SIZE
# 诊断
def check_parallel_config(world_size, tp, pp, cp, ep, dp):
    product = tp * pp * cp * ep * dp
    if product != world_size:
        raise ValueError(
            f"并行维度乘积 {product} (TP={tp}×PP={pp}×CP={cp}×EP={ep}×DP={dp}) "
            f"不等于 WORLD_SIZE={world_size}"
        )
```

**Q: NCCL初始化超时**

```bash
# 诊断: 检查网络配置、IB可用性
export NCCL_DEBUG=INFO
export NCCL_SOCKET_IFNAME=eth0  # 或ib0
nccl-tests/build/all_reduce_perf -b 8M -e 512M -f 2 -g 1
```

### 5.2 性能问题

**Q: GPU利用率低**

排查步骤:
1. 查看Profiler输出，确认瓶颈是在计算还是通信
2. 检查流水线气泡比例: `bubble = (pp_size - 1) / num_microbatches`
3. 确认数据加载是否成为瓶颈 (DataLoader `num_workers`)

**Q: OOM (显存溢出)**

排查步骤:
1. 减小 `--micro-batch-size`
2. 启用 `--recompute-granularity=full`
3. 启用 `--sequence-parallel` (与TP搭配使用)
4. 增加 `--context-parallel-size` (处理长序列)
5. 使用 `--use-distributed-optimizer` (节省优化器状态内存)
