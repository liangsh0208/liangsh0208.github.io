## 1. 项目定位

DeepEP 是 DeepSeek 为**超大规模 MoE 模型**（如 DeepSeek-V3/R1）量身打造的通信库。在 MoE 架构中，每个 Token 需要被路由到若干"专家"GPU 上计算，这一过程被称为 **Expert Parallelism（EP）**，其核心操作是：

- **Dispatch（分发）**：将 Token 从当前 GPU 发送到对应专家所在的 GPU
- **Combine（聚合）**：各专家计算完毕后，将结果发回原始 GPU 进行加权求和

这两个操作本质上是一次**不规则的 All-to-All 通信**，其效率直接决定了 MoE 模型的端到端训练/推理速度。

DeepEP 专注于优化这两个操作，提供：
- **高吞吐 Normal 内核**：面向训练和推理 Prefilling，利用 NVLink + RDMA 并发转发
- **低延迟 LL 内核**：面向推理 Decoding，纯 RDMA 路径，延迟最低

## 2. 核心功能

### 2.1 三种通信模式

| 模式 | 适用场景 | 硬件路径 | 延迟特征 |
|------|---------|---------|---------|
| Intranode（节点内） | ≤ 8 GPU 单机 EP | 纯 NVLink | 极低延迟，高带宽 |
| Internode（跨节点） | > 8 GPU 多机 EP | NVLink + RDMA | 中等延迟，带宽受 RDMA 限制 |
| Low-latency（低延迟） | 推理 Decode EP | 纯 RDMA（IBGDA） | 极低延迟，SM 资源几乎为零 |

### 2.2 数据精度支持

- **BF16**：默认格式，Combine 操作输出
- **FP8（E4M3）**：Dispatch 支持 FP8 压缩传输，减少带宽消耗
- **UE8M0**（可选）：将 FP8 缩放因子压缩为 8-bit 整数指数格式

### 2.3 性能数据（H800 + InfiniBand 400Gb/s）

**Normal 内核（DeepSeek-V3 训练设置：4096 tokens, hidden=7168, top-8 experts）**

| 类型 | Dispatch EP 规模 | 瓶颈带宽 | Combine EP 规模 | 瓶颈带宽 |
|------|----------------|---------|----------------|---------|
| 节点内 | 8 | 153 GB/s (NVLink) | 8 | 158 GB/s (NVLink) |
| 跨节点 | 16 | 43 GB/s (RDMA) | 16 | 43 GB/s (RDMA) |
| 跨节点 | 64 | 51 GB/s (RDMA) | 64 | 50 GB/s (RDMA) |

**低延迟内核（128 tokens, hidden=7168, top-8 experts）**

| Dispatch EP 规模 | 延迟 | Combine EP 规模 | 延迟 |
|----------------|-----|----------------|-----|
| 8 | 77 µs | 8 | 114 µs |
| 32 | 155 µs | 32 | 273 µs |
| 128 | 192 µs | 128 | 369 µs |

## 4. 与 MoE/EP 训练的关系

在标准 MoE 前向计算流程中，DeepEP 占据了通信核心位置：

```
Input Tokens (本地 GPU)
       │
       ▼
  [Gate 路由计算]
  topk_idx, topk_weights
       │
       ▼
  get_dispatch_layout()   ← layout.cu
  → num_tokens_per_rank   (每个 rank 需要接收多少 token)
  → is_token_in_rank      (token 到 rank 的映射矩阵)
       │
       ▼
  Buffer.dispatch()       ← intranode.cu / internode.cu
  → recv_x                (接收到的 token 张量)
  → recv_topk_idx         (本地化的专家索引)
  → handle                (供 combine 使用的通信句柄)
       │
       ▼
  [本地专家计算]
  FFN(recv_x)
       │
       ▼
  Buffer.combine()        ← intranode.cu / internode.cu
  → combined_x            (加权求和后的输出)
       │
       ▼
  Output Tokens (本地 GPU)
```

反向传播时，dispatch 的梯度通过 combine 实现，combine 的梯度通过 dispatch 实现（数学上互为转置）。

## 5. 关键设计理念

### 5.1 双通道缓冲区（NVLink + RDMA 分离）

跨节点场景下，DeepEP 将通信分为两个物理层：
- **NVLink 缓冲区**：节点内 8 个 GPU 间的直接内存访问，带宽约 160 GB/s
- **RDMA 缓冲区**（NVSHMEM 对称内存）：跨节点 RDMA 传输，带宽约 50 GB/s

Token 先通过 RDMA 到达目标节点，再经由节点内 NVLink 分发到正确的 GPU。

### 5.2 分通道队列（Channel-Based Queue）

通信缓冲区被划分为 `num_sms/2` 个通道（channel），每个通道独立管理发送/接收队列。这使得：
- 多 SM 并发工作，互不阻塞
- 发送方使用 tail 指针，接收方使用 head 指针，形成无锁生产者-消费者模型

### 5.3 SM 资源可控

Normal 内核通过 `Buffer.set_num_sms(n)` 静态控制参与通信的 SM 数量，剩余 SM 完全可以做计算（GEMM），实现通信-计算重叠。

### 5.4 Hook-Based 重叠（低延迟模式）

低延迟内核引入了 **接收 Hook** 机制：`low_latency_dispatch(return_recv_hook=True)` 只发出 RDMA 写请求，不等待数据到达。用户可在此期间完成其他计算（如 Attention），然后调用 `hook()` 等待数据真正就绪。整个等待过程不占用任何 SM。

## 7. 快速上手

```python
from deep_ep import Buffer, EventOverlap

# 控制使用的 SM 数量（建议 20-24，留出 SM 给 GEMM）
Buffer.set_num_sms(24)

# 初始化通信缓冲区（需要在分布式初始化之后调用）
buffer = Buffer(group, num_nvl_bytes, num_rdma_bytes)

# 训练/Prefilling 场景
recv_x, recv_topk_idx, recv_topk_weights, num_recv_per_expert, handle, event = \
    buffer.dispatch(x, topk_idx=topk_idx, topk_weights=topk_weights, ...)

# 计算后归并
combined_x, _, event = buffer.combine(expert_output, handle, ...)

# Decoding 低延迟场景
recv_x, recv_count, handle, event, hook = \
    buffer.low_latency_dispatch(x, topk_idx, num_max_tokens, num_experts, return_recv_hook=True)
hook()  # 等待 RDMA 接收完成（不占 SM）
```
