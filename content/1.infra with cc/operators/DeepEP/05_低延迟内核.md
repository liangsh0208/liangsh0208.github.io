# 05 低延迟内核（Low-Latency Kernels）

> 源文件：`csrc/kernels/internode_ll.cu`、`csrc/config.hpp`（LowLatencyLayout）

---

## 1. 模块作用与设计动机

低延迟（LL）内核专为**推理 Decoding 场景**设计。Decoding 阶段的特点是：
- **极小 batch size**（通常 1~256 tokens/rank，远小于训练的 4096）
- **每步推理反复执行**（自回归生成数百步）
- **延迟直接影响用户体验**（每步延迟越低越好）

与 Normal 内核相比，LL 内核做了以下取舍：

| 特性 | Normal 内核 | Low-Latency 内核 |
|------|------------|-----------------|
| 通信路径 | NVLink + RDMA 两段式 | 纯 RDMA（IBGDA 直达） |
| SM 占用 | 可配置（如 24 SM） | 接近 0（hook 模式完全无 SM） |
| 预分配 | 动态（按实际 token 数） | 静态（按最大 token 数预分配） |
| CUDA Graph 兼容 | 不兼容（CPU 等待 GPU 信号） | 兼容 |
| 缓冲区策略 | 队列（环形缓冲区） | 双缓冲（Ping-Pong） |
| 节点内加速 | NVLink | NVLink（当 allow_nvlink=True 时） |

## 2. 核心数据结构

### 2.1 LowLatencyLayout（`config.hpp`）

```cpp
struct LowLatencyBuffer {
    void* dispatch_rdma_send_buffer;     // 本地构造消息的暂存区
    void* dispatch_rdma_recv_data_buffer; // 接收远端 dispatch 消息的区域（对称内存）
    int*  dispatch_rdma_recv_count_buffer; // 每个 expert 接收到的 token 计数

    void* combine_rdma_send_buffer;       // 本地 combine 消息暂存区
    void* combine_rdma_recv_data_buffer;  // 接收 combine 消息的区域
    int*  combine_rdma_recv_flag_buffer;  // combine 完成标志
};

struct LowLatencyLayout {
    LowLatencyBuffer buffers[2];  // Ping-Pong 双缓冲
    size_t total_bytes;
};
```

**RDMA 内存布局（地址顺序）**：

```
[signaling_0][signaling_1][send_0][send_1][recv_0][recv_1]
  ↑ 每个 expert 的计数器/标志位（int 数组，对称内存）
                             ↑ 发送暂存区（仅本地读写）
                                          ↑ 接收区（NVSHMEM 对称，对端直接写入）
```

### 2.2 消息格式

**Dispatch 消息**（每个 token 一条）：
```
[int4 元数据: {src_token_idx, reserved0, reserved1, reserved2}]
[hidden 数据: fp8_hidden + scales，或 bf16_hidden]
```

**Combine 消息**（每个专家处理后的 token）：
```
[per-128-channel scales (nv_bfloat162)]
[hidden 数据: bf16_hidden]
```

### 2.3 QP 分配策略

低延迟模式要求 `num_qps_per_rank == num_local_experts`，即每个本地专家拥有独立的 QP（Queue Pair）：

```python
# 初始化时指定
_buffer = Buffer(group, 0, num_rdma_bytes, low_latency_mode=True,
                 num_qps_per_rank=num_experts // group.size())
```

这使得不同专家的 RDMA 操作完全并行，无 QP 争用。

## 3. dispatch Kernel 实现

### 3.1 两阶段设计（phases 参数）

LL dispatch kernel 支持两个独立阶段，通过 `phases` 参数控制：

```cpp
#define LOW_LATENCY_SEND_PHASE 1
#define LOW_LATENCY_RECV_PHASE 2

// phases = 3 (SEND | RECV)：单次调用完成发送和接收
// phases = 1：仅发送（hook 模式：发出 RDMA 请求后立即返回）
// phases = 2：仅接收（hook 调用：等待接收并打包结果）
```

### 3.2 发送阶段（warp_id < num_warps - 1）

```cpp
// 每个 warp 处理一个 token
for (int token_idx = sm_id; token_idx < num_tokens; token_idx += num_sms) {
    // 1. FP8 量化（如果启用）
    auto amax = reduce_amax(x[token_idx * hidden : (token_idx+1) * hidden]);
    calculate_fp8_scales(amax, scale, scale_inv, round_scale);

    // 2. 构造消息：写入 rdma_x（本地发送缓冲区）
    *rdma_x_src_idx = token_idx;           // 源 token 索引
    convert_to_fp8(rdma_x_vec, x, scale); // FP8 数据
    rdma_x_scales[channel] = scale_inv;   // 缩放因子

    // 3. 对所有选中的专家发出 RDMA PUT
    for (int topk in topk_idx[token_idx]) {
        if (topk < 0) continue;
        dst_rank = topk / num_local_experts;
        local_expert = topk % num_local_experts;
        slot_idx = atomicAdd(counter_per_expert + topk, 1);  // 原子获取槽位

        dst_ptr = rdma_recv_data_buffer + local_expert * num_ranks * max_tokens * msg_size
                  + rank * max_tokens * msg_size + slot_idx * msg_size;

        // P2P 优先，退而 RDMA
        auto p2p_ptr = nvshmemi_get_p2p_ptr(dst_ptr, rank, dst_rank);
        if (p2p_ptr == 0)
            nvshmemi_ibgda_put_nbi_warp(dst_ptr, rdma_x_src_idx, msg_size, dst_rank, local_expert, lane_id, slot_idx);
        else
            UNROLLED_WARP_COPY(8, lane_id, num_int4, p2p_ptr, src, ld_nc_global, st_na_global);

        atomic_add_release(finish_counter + topk, 1);  // 通知 count 发送 warp
    }
}
```

### 3.3 计数发送（最后一个 warp，sm_id == 0）

```cpp
// 等待本地所有发送完成（通过 finish_counter）
// 然后通过 RDMA 原子操作更新对端的 recv_count
while (finish_counter[expert] != FINISHED_SUM_TAG * 2) { spin; }

// 发送 count（使用 RMA Atomic Add）
nvshmemi_ibgda_amo_nonfetch_add(
    rdma_recv_count + local_expert * num_ranks + rank,  // 对端计数器
    -num_tokens_sent - 1,   // 负值编码：区分"0个token"和"未写入"
    dst_rank, local_expert_qp_id
);
```

**关键技巧**：将计数写成 `-(N+1)` 的形式：
- 初始值为 0，表示"未接收到任何计数消息"
- 接收到计数 N 后变为 `-(N+1)`
- 接收方检查 `value < 0` 来判断是否已收到计数

### 3.4 接收阶段（recv_phase）

```cpp
// 每个 SM-warp-group 负责一个 (expert, src_rank) 对
if (responsible_expert_idx < num_experts) {
    // sub_warp 1：等待 RDMA 计数到达
    if (sub_warp_id == 1 and lane_id == 0) {
        while ((count = ld_acquire_sys(rdma_recv_count + expert * num_ranks + src_rank)) == 0) {
            if (timeout) {
                mask_rank(src_rank);  // shrink 模式：超时后屏蔽 rank
                break;
            }
        }
        num_recv_tokens = -count - 1;  // 解码
        begin_idx = atomicAdd(packed_recv_count + expert, num_recv_tokens);
        recv_range[src_rank] = pack2(num_recv_tokens, begin_idx);  // 记录范围
    }

    // sub_warp 0（与 warp 1 并行）：复制 token 数据
    for (int i = sub_warp_id; i < num_recv_tokens; i += num_warps_per_group) {
        // 复制 hidden 数据（ld_nc_global 跳过 L1 缓存）
        UNROLLED_WARP_COPY(7, lane_id, hidden_int4, dst, src, ld_nc_global, st_na_global);

        // 复制 FP8 scales（转置存储：column-major for TMA 兼容性）
        // 目标布局：[num_tokens, num_packed, num_elems_per_pack] 在 column-major 排列
        if constexpr (kUseFP8) {
            // pack_stride = num_ranks * max_tokens * num_elems_per_pack
            recv_x_scales[token_idx * token_stride + pack_idx * pack_stride + elem_idx] = scale;
        }
    }
}
```

## 4. combine Kernel 实现

### 4.1 发送阶段

```cpp
// 构造 combine 消息：scales + hidden_bf16
// combine 消息格式：[per-128-channel min/max (bf162)] + [hidden (bf16)]
// 使用 LogFMT（可选）：动态 per-64-channel 压缩到 10 bit

for (token in expert_assigned_tokens) {
    // 打包 combine 消息到 rdma_send_buffer
    auto msg = combine_send_buffer + token * num_bytes_per_combine_msg;
    // 写入 scales
    for (ch in num_scales)
        msg.scales[ch] = {min, max} of channel ch;  // bf162
    // 写入 hidden 数据
    memcpy(msg.hidden, x + token * hidden, hidden_bytes);

    // RDMA PUT 到源 rank（src_rank = token 最初来自哪个 rank）
    dst_ptr = combine_recv_buffer_on_src_rank + expert * max_tokens * msg_size + slot * msg_size;
    nvshmemi_ibgda_put_nbi_warp(dst_ptr, msg, msg_size, src_rank, qp_id, ...);

    // 更新 flag：-1 表示已发送
    nvshmemi_ibgda_amo_nonfetch_add(combine_recv_flag + expert, -1, src_rank, qp_id);
}
```

### 4.2 接收与归并阶段

```cpp
// 等待所有来源的 combine 数据到达（flag 变为负值）
while (combine_recv_flag[expert * num_ranks + src_rank] == 0) { spin-wait; }

// 加权归并：recv_combined_x[token_idx] += weight * received_expert_output
for (token in received_tokens_from_src_rank) {
    auto weight = topk_weights[token_original_idx][topk_pos];
    // BF16 加权累加
    for (ch in hidden)
        combined_x[token_original_idx][ch] += weight * received_hidden[ch];
}
```

## 5. Hook 机制：无 SM 重叠

### 5.1 工作原理

```python
# 方式 1：阻塞等待（默认）
recv_x, recv_count, handle, event, _ = buffer.low_latency_dispatch(
    x, topk_idx, num_max_tokens, num_experts,
    async_finish=False, return_recv_hook=False)
# 返回时数据已确保到达

# 方式 2：Hook 模式（推荐用于双 micro-batch 重叠）
recv_x, recv_count, handle, event, hook = buffer.low_latency_dispatch(
    x, topk_idx, num_max_tokens, num_experts,
    async_finish=True, return_recv_hook=True)
# 此时仅发出了 RDMA 请求，数据可能还在传输

# 在此期间可以做计算（如 Attention）
do_attention_computation()

# 调用 hook：等待 RDMA 接收完成（pure CPU spin-wait 或 GPU event）
hook()  # 不占用任何 SM
```

### 5.2 双 micro-batch 重叠示意

```
Timeline（GPU 时间线）：
                  Batch A                Batch B
Compute stream: [Attention A] [MoE A]    [Attention B] [MoE B]
Comm background:      [RDMA dispatch A]       [RDMA dispatch B]
                                   hook A()        hook B()
```

RDMA 传输发生在 NIC 硬件层面，完全不占用 GPU SM。`hook()` 只是一个 CPU 轮询或 GPU fence，等待 NIC 写入完成信号。

## 6. Shrink 模式：容错处理

LL 内核支持动态屏蔽故障 rank（`enable_shrink=True`）：

```python
# 查询当前屏蔽状态
mask_status = torch.zeros(num_ranks, dtype=torch.int, device='cuda')
buffer.low_latency_query_mask_buffer(mask_status)

# 手动屏蔽某个 rank
buffer.low_latency_update_mask_buffer(rank_to_mask=3, mask=True)

# 发生超时时自动屏蔽（内部逻辑）
if (wait_recv_cost > NUM_TIMEOUT_CYCLES):
    atomicExch(mask_buffer_ptr + src_rank, 1)
```

屏蔽的 rank 在后续通信中被跳过（`is_rank_masked` 检查），保证其他 rank 不受影响。

## 7. FP8 缩放因子布局优化

低延迟 dispatch 的 FP8 scales 使用**列优先（column-major）** 存储：

```
目标格式（CuTe compatible）：
  (num_tokens, (num_packed, num_elems_per_pack)) : (num_elems_per_pack, (num_tokens * num_elems_per_pack, 1))

实际含义：对于 hidden=7168，num_scales=56（7168/128）：
  num_elems_per_pack = 4（float32 / uint8 比例）或 1
  pack_stride = num_ranks * max_tokens * 4
```

这种布局设计为后续 TMA（Tensor Memory Accelerator）读取 scales 优化。

## 8. 性能调优建议

### 8.1 num_max_dispatch_tokens_per_rank 的选择

```python
# 推荐 ≤ 256，越小内存越省，但不能小于实际 batch size
# QP depth 约束：nvshmem_qp_depth >= (num_max_dispatch_tokens_per_rank + 1) * 2
assert buffer.nvshmem_qp_depth >= (num_max_dispatch_tokens_per_rank + 1) * 2
```

### 8.2 allow_nvlink_for_low_latency_mode

```python
# 默认 True：允许 NVSHMEM 使用 NVLink，节点内通信更快
# 但与 hook-based 重叠不完全兼容（NVLink 路径会分配 SM）
Buffer(group, 0, rdma_bytes, low_latency_mode=True,
       allow_nvlink_for_low_latency_mode=False)  # 纯 RDMA，最适合 hook 重叠
```
