UpdateWeightFromDistributed 状态机

update_weights()
  ├── pause_generation()          ← SGLang 暂停接收新请求
  ├── flush_cache()               ← 清空 KV cache
  ├── barrier()                   ← GLOO
  ├── for each non-expert param:
  │     ├── all_gather_param()    ← TP allgather
  │     ├── convert_to_hf()       ← Megatron → HF
  │     ├── bucket buffer          ← 累积到 buffer_size > threshold 后 flush
  │     └── broadcast to engines   ← dist.broadcast() / remote update
  ├── barrier()
  ├── for each expert param:
  │     ├── EP gather             ← expert model parallel gather
  │     └── broadcast
  ├── barrier()
  ├── post_process_quantization()  ← int4 反量化
  ├── continue_generation()        ← SGLang 恢复
  └── barrier()

10. 时间线分析

gantt title 一个 Rollout 的 Wall-Clock 时间线（Colocate 模式） dateFormat X axisFormat %s section SGLang generate response : 0, 3 non_generation (scheduling) : 0, 0.5 section Megatron log_probs (ref + actor) : 3, 4.5 compute_advantages : 4.5, 5 train (fwd + bwd + opt) : 5, 8 log_rollout_data : 3, 3.1 log_perf_data : 8, 8.1 section Sync offload sglang : 2.8, 3 update_weights : 8, 8.5 onload sglang : 8.5, 8.6 section Wait train_wait (idle) : 0, 0.3
⚠️ 关键洞察：在 colocate 模式下，generate 和 train 无法并行，因为独占同一组 GPU。训练吞吐公式：
effective throughput = samples_per_rollout / (generate_time + train_time + sync_time)
在分离部署模式下理论上可以 overlap generate_{N+1} 和 train_N（如果实现 async pipeline）。

诊断工具栈

训练端诊断

  • train/* 日志 — 学习动力学
  • perf/* 日志 — 时间分解
  • rollout/* 日志 — 生成质量
  • PyTorch Profiler Chrome Trace — NCCL 通信
  • nvidia-smi dmon — GPU 利用率

推理端诊断

  • SGLang metrics endpoint — decode token/s
  • Prefix cache hit rate — KV 复用
  • Speculative decoding accept rate
  • Router 负载均衡 — dp_rank 分布
  • CUDA Graph hit rate
💡 一句话总结：slime 是一个典型的"Ray 调度 + Megatron 训练 + SGLang 推理"三层分离架构。性能优化的核心矛盾永远是在 generate（memory-bound）和 train（compute-bound）之间的 GPU 时间分配。MFU 只覆盖了 train 阶段的计算效率，端到端的 wall-clock throughput 才是真正的优化目标。
