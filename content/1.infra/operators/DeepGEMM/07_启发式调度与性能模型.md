## 1. 为什么需要启发式

不同的矩阵形状（M/N/K）对应不同的最优 block size 配置：

- **大 M 大 N**：适合大 tile（BLOCK_M=128, BLOCK_N=256），最大化 TC 利用率
- **小 M 大 N**（如 decode 阶段）：适合小 tile（BLOCK_M=16 或 32），避免 wave 浪费
- **N 为奇数倍**：TMA multicast 可能失效，需要 fallback 到 cluster_size=1

DeepGEMM 的启发式**不是查表**，而是对所有合法配置进行枚举，建立性能模型估算每个配置的执行周期，选择估算最快的配置。

## 2. 配置结构体层次

```cpp
// csrc/jit_kernels/heuristics/config.hpp

// GEMM 问题描述（输入）
struct GemmDesc {
    GemmType gemm_type;     // Normal / MGroupedContiguous / Masked / KGrouped / Batched
    KernelType kernel_type; // Kernel1D1D / Kernel1D2D / KernelNoSF
    int m, n, k, num_groups;
    at::ScalarType a_dtype, b_dtype, cd_dtype;
    cute::UMMA::Major major_a, major_b;
    bool with_accumulation;
    int num_sms, tc_util;
    std::string compiled_dims;
    // 启发式用的"期望"维度（用于不规则分组时的配置估算）
    int expected_m, expected_n, expected_k, expected_num_groups;
};

// tile 布局配置
struct Layout {
    int swap_ab;             // 是否交换 A/B（用于 TN/TT 布局）
    int block_m, block_n, block_k;
    int cluster_m, cluster_n;  // SM cluster 大小（SM90 multicast）
};

// 共享内存存储配置
struct StorageConfig {
    int load_block_m, load_block_n;    // TMA load 的实际 block 大小
    int store_block_m, store_block_n;  // TMA store 的实际 block 大小
    int swizzle_a_mode, swizzle_b_mode;  // SMEM swizzle 字节数
    int swizzle_cd_mode;                 // 输出 swizzle
};

// 流水线配置
struct PipelineConfig {
    int smem_size;   // 总共享内存字节数
    int num_stages;  // 流水线 stage 数
};

// kernel 启动配置
struct LaunchConfig {
    int num_sms;              // 启动的 SM 数
    int num_sms_per_cluster;  // 每个 cluster 的 SM 数
    int num_threads;          // 每个 block 的线程数
    int num_tma_threads, num_math_threads;      // SM90 线程分配
    int num_non_epilogue_threads, num_epilogue_threads; // SM100 线程分配
};
```

## 3. 候选配置枚举（SM90 为例）

```cpp
// csrc/jit_kernels/heuristics/sm90.hpp
struct SM90ArchSpec {
    static constexpr int smem_capacity = 232448;  // SM90 每 SM 共享内存 232KB

    static std::vector<Layout> get_layout_candidates(const GemmDesc& desc) {
        // Block M 候选
        std::vector<int> block_m_candidates = {64, 128};
        if (desc.m <= 16) block_m_candidates.push_back(16);
        if (desc.m <= 32) block_m_candidates.push_back(32);
        if (desc.cd_dtype != torch::kFloat)  // BF16 输出可用更大 M
            block_m_candidates.push_back(256);

        // Block N 候选（步长 = lcm(16, block_n_multiple_of)）
        int step = std::lcm(16, get_block_n_multiple_of());
        // 1D1D kernel 特殊：最小从 24 开始（避免 FP32 输出 bank conflict）
        int start = (kernel_type == Kernel1D1D) ? 24 : step;
        // 寄存器限制：1D2D 最大 192，1D1D 最大 160，其他 256
        int end = 256;
        if (kernel_type == Kernel1D2D) end = 192;
        if (kernel_type == Kernel1D1D) end = 160;

        // cluster 候选（1×1 或 1×2 或 2×1，最多 2 SM cluster）
        for (int cluster_m = 1; cluster_m <= 2; ++cluster_m) {
            for (int cluster_n = 1; cluster_n <= 2; ++cluster_n) {
                if (cluster_m * cluster_n > 2) continue;
                if (desc.num_sms % (cluster_m * cluster_n) != 0) continue;

                for (int block_m: block_m_candidates) {
                    for (int block_n: block_n_candidates) {
                        // 过滤不合法的组合
                        auto layout = Layout{0, block_m, block_n, block_k, cluster_m, cluster_n};
                        auto storage = get_storage_config(desc, layout);

                        // swizzle 至少 64 字节（32 字节性能差）
                        if (storage.swizzle_a_mode % 64 != 0) continue;

                        // 流水线 stage 至少 3（小矩阵至少 4）
                        auto pipeline = get_pipeline_config(desc, layout, storage);
                        if (pipeline.num_stages < 3) continue;
                        if (block_m * block_n < 128*192 && pipeline.num_stages < 4) continue;

                        candidates.push_back(layout);
                    }
                }
            }
        }
        return candidates;
    }
};
```

## 4. Swizzle 模式计算

Swizzle 模式由 tile 的"内维度"大小决定：

```cpp
// csrc/jit_kernels/heuristics/utils.hpp
static int get_swizzle_mode(int inner_dim_size, int elem_bytes) {
    // swizzle 字节数 = inner_dim_elements * elem_bytes
    // 但需要是 16/32/64/128 的幂次
    const int total_bytes = inner_dim_size * elem_bytes;
    if (total_bytes >= 128) return 128;
    if (total_bytes >= 64)  return 64;
    if (total_bytes >= 32)  return 32;
    return 16;  // 最小（退化为 interleave）
}
```

对于 FP8（1 字节）+ K-major（inner_dim = BLOCK_K = 128）：`128 × 1 = 128`，选择 128B swizzle（B128）。

## 5. 流水线 stage 数计算

在共享内存容量约束下最大化 stage 数：

```cpp
static PipelineConfig get_pipeline_config(...) {
    constexpr int kNumMaxStages = 16;

    // 固定占用（不随 stage 变化）
    const int smem_cd      = align(block_m * block_n * cd_elem_size, 1024);
    const int smem_barriers = kNumMaxStages * 8 * 2;  // 两组 barrier

    // 每个 stage 的占用
    const int smem_a_per_stage = load_block_m * block_k * a_elem_size;
    const int smem_b_per_stage = load_block_n * block_k * b_elem_size;
    const int smem_sfa_per_stage = align(block_m * 4, 128);  // FP32 scale
    const int smem_sfb_per_stage = align(block_n * 4, 128);

    const int smem_per_stage = smem_a + smem_b + smem_sfa + smem_sfb;
    const int num_stages = min(
        (smem_capacity - smem_cd - smem_barriers) / smem_per_stage,
        kNumMaxStages
    );
    return {smem_cd + smem_barriers + num_stages * smem_per_stage, num_stages};
}
```

SM90 有 232KB 共享内存（`smem_capacity = 232448`），典型配置（BLOCK_M=128, BLOCK_N=128, FP8）：

```
smem_cd = 128 * 128 * 4 = 65536 B（FP32 输出）
smem_per_stage = 128*128*1 + 128*128*1 + 128*4 + 128*4 = 33792 B
num_stages = (232448 - 65536 - ...) / 33792 ≈ 4 stages
```

## 6. 性能模型：周期估算

这是 DeepGEMM 启发式的核心，对每个候选配置估算执行周期：

```cpp
static LayoutInfo get_layout_info(const GemmDesc& desc, const Layout& layout) {
    const auto num_blocks = ceil_div(m, block_m) * ceil_div(n, block_n) * num_groups;
    const auto num_waves  = ceil_div(num_blocks, desc.num_sms);

    // 带宽参数（H100 近似值）
    const int l2_bw  = min(64.0 * num_sms, 8e6 / 1.3e3);  // B/cycle
    const int l1_bw  = 128 * num_sms;                       // B/cycle
    const int elem_ab = c10::elementSize(a_dtype);
    const int elem_cd = c10::elementSize(cd_dtype);

    // 每个 block 的数据移动量
    // L2 带宽：考虑 multicast 效果（cluster 内 B 只 load 一次）
    int64_t num_bytes_l2_ab = expected_k *
        (block_m / cluster_n + block_n / cluster_m) * elem_ab;
    // L1 带宽：SM 内 SMEM → RF 的数据量
    int64_t num_bytes_l1_ab = expected_k * (block_m + block_n) * elem_ab;
    // TC 带宽（L1 → Tensor Core）
    int64_t num_bytes_l1_tc = expected_k *
        (max(64, block_m) + block_n) * elem_ab + block_m * block_n * elem_cd;
    // 输出 HBM 带宽（含 C 矩阵读取）
    int64_t num_bytes_l1_l2_cd = block_m * block_n * elem_cd * (with_accumulation ? 2 : 1);

    // 总周期 = max(L2 bound, L1 bound)，再除以 wave 效率
    float wave_efficiency = (float)num_blocks / (num_waves * num_sms);
    int64_t num_l2_cycles = (num_bytes_l2_ab + num_bytes_l1_l2_cd) * num_blocks / l2_bw;
    int64_t num_l1_cycles = (num_bytes_l1_ab + num_bytes_l1_tc + num_bytes_l1_l2_cd) * num_blocks / l1_bw;
    int64_t num_cycles = max(num_l1_cycles, num_l2_cycles) / wave_efficiency;

    // 单 wave 时 multicast 无意义，禁用
    if (layout.cluster_size() > 1 && num_waves <= 1)
        num_cycles = INT64_MAX;

    return {num_waves, last_wave_util, num_cycles, layout};
}
```

关键洞察：

1. **L1/L2 分别建模**：L2 受 multicast 影响，L1 主要受 TC 操作量影响，取较大者
2. **Wave 效率**：`num_blocks / (num_waves × num_sms)` — 最后一波如果只跑了少量 block，整体效率下降
3. **Multicast 在单 wave 时无效**：cluster 启动有额外开销，单 wave 时不用 multicast 更快

## 7. 配置选择流程

```cpp
// csrc/jit_kernels/heuristics/common.hpp
template <typename ArchSpec>
static GemmConfig get_best_config(const GemmDesc& desc) {
    // 1. 枚举所有合法候选
    const auto layout_candidates = ArchSpec::get_layout_candidates(desc);

    // 2. 对每个候选估算周期，选最小的
    auto best_layout = layout_candidates[0];
    auto best_info   = ArchSpec::get_layout_info(desc, best_layout);
    for (const auto& candidate: layout_candidates) {
        const auto info = ArchSpec::get_layout_info(desc, candidate);
        if (ArchSpec::compare(info, best_info))
            best_layout = candidate, best_info = info;
    }

    // 3. 根据最优 layout 推导其他配置
    const auto storage  = ArchSpec::get_storage_config(desc, best_layout);
    const auto pipeline = ArchSpec::get_pipeline_config(desc, best_layout, storage);
    const auto launch   = ArchSpec::get_launch_config(desc, best_layout);

    // 4. 打印（若开启 DG_PRINT_CONFIGS）
    if (get_env("DG_PRINT_CONFIGS")) {
        std::cout << desc << ": GemmConfig(...) LayoutInfo(...)" << std::endl;
    }

    return {best_layout, storage, pipeline, launch};
}
```

```cpp
// csrc/jit_kernels/heuristics/runtime.hpp
class HeuristicsRuntime {
    int num_sms = 0;    // 当前使用的 SM 数（0 = 全部）
    int tc_util = 80;   // 近似 TC 利用率百分比（用于 L1/L2 bandwidth 修正）
    int mk_alignment = 0;  // M/K 对齐（MoE contiguous）
    int block_n_multiple_of = 1;  // block N 必须是该值的倍数

public:
    int get_num_sms() const {
        return num_sms > 0 ? num_sms : device_runtime->total_sm_count;
    }
};
```

TC 利用率如何影响性能模型：理论上 `tc_util=80` 意味着 80% 时间在做 TC 计算，20% 时间在等 L1/L2 数据，这会影响 bandwidth bottleneck 的判断。

## 10. 实际调优建议

1. **开启 `DG_PRINT_CONFIGS=1`**：观察每个形状选择的 config，理解启发式决策

2. **设置 `expected_m/n/k`**：当实际维度分布不均（如 MoE 不同专家 token 数不同），通过 expected 维度让启发式选更合适的 config：
   ```cpp
   desc.expected_m = average_tokens_per_expert;
   desc.expected_k = max_k_among_groups;  // K-grouped GEMM
   ```

3. **调整 `set_block_size_multiple_of`**：如果你的 N 总是 256 的倍数，可以设置为 128，减少候选数量，同时可能选到更大的 block_n

4. **`set_tc_util`**：如果实际 TC 利用率很低（如小 M decode），调低此值让启发式更倾向选小 tile 以减少 wave 浪费
