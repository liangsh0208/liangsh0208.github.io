Megatron Infra / CUDA / Trace 性能优化实战手册

面向大模型训练 Infra、GPU 性能优化、CUDA Kernel、NCCL 通信和系统调优的实践路线。重点不是背参数，而是建立“现象 → Trace → 根因 → 优化 → 验证”的工程闭环。

0. 学习目标

目标岗位包括：Megatron InfraTraining InfraCUDA Performance EngineerGPU System EngineerDistributed Training Engineer

最终要能解决的问题

  • GPU 利用率只有 30%～50%，能定位是 CPU、DataLoader、NCCL、Kernel 还是 IO。
  • 多机训练扩展效率差，能分析 rank mapping、IB、NUMA、NCCL 算法和通信重叠。
  • Kernel 很慢，能判断 compute bound / memory bound，并从 shared memory、寄存器、warp stall、Tensor Core 角度优化。
  • Megatron 训练吞吐下降，能用 trace 证明瓶颈，并给出可复现实验。

1. 性能工程工作流

不要先改参数，也不要先写 kernel。第一步永远是把问题变成可观测、可复现、可对比的 trace。

每次优化都要有 baseline、实验变量、trace 证据和收益数据。否则只是“调参玄学”。
# 建议每个实验都记录这些字段
experiment_id: llama_7b_8gpu_tp1_pp1_dp8_baseline
hardware: 8xA100-80G, NVSwitch
software: CUDA, NCCL, PyTorch, Megatron commit
model: layers, hidden, heads, seq_len, global_batch
metrics: tokens/s, MFU, step_time, GPU busy, NCCL time, dataloader wait
trace: nsys report path, ncu report path
change: 本次只改一个变量
result: 改动前后对比

2. Trace 分析核心

Trace 的目标是回答：GPU 是在算、在等通信、在等 CPU、在等数据，还是在等 IO。

2.1 正常训练 step 的理想形态

2.2 三种常见坏 trace

GPU 空洞：CPU/DataLoader 问题

典型根因：数据预处理慢、Python GIL、worker 不够、磁盘 IO、CPU affinity 错误、H2D copy 没有 overlap。

NCCL 暴露：通信没被隐藏

典型根因：bucket 太大/太小、stream event 依赖错误、跨节点带宽差、rank mapping 不合理、TP/PP 放到了慢链路。

Kernel 细碎：launch overhead

典型根因：算子未融合、动态图 graph break、batch 太小、CUDA Graph 未启用。

Straggler：某些 rank 慢

典型根因：某 GPU 降频/ECC、NUMA 错绑、网卡拥塞、数据 shard 不均、MoE expert load imbalance。

3. Nsight Systems 实战

Nsight Systems 用来看端到端时间线：CPU、CUDA API、GPU kernel、Memcpy、NCCL、OS runtime。它回答的是“时间花在哪里”。

3.1 最小采集命令

# 单机示例
nsys profile \
  -o reports/llama7b_step \
  --trace=cuda,nvtx,osrt,cudnn,cublas \
  --capture-range=cudaProfilerApi \
  --capture-range-end=stop \
  python pretrain_gpt.py ...

# 多机建议每个 rank 单独输出，至少采 rank0、每个节点一个本地 rank、疑似慢 rank
nsys profile -o reports/node${NODE_RANK}_rank${LOCAL_RANK} --trace=cuda,nvtx,osrt python train.py

3.2 Trace 阅读顺序

  1. 先看 step 周期是否稳定：有没有长尾 step。
  2. 看 GPU row：是否有大空白。如果有，先别看 kernel，先看 CPU/CUDA API/DataLoader。
  3. 看 NCCL row：通信是否与 backward overlap，还是串行暴露。
  4. 看 CUDA API：是否大量 cudaStreamSynchronize、cudaMemcpy、cudaMalloc。
  5. 看 kernel pattern：是否 GEMM 很大、elementwise 很碎、attention 是否异常慢。
  6. 跨 rank 对比：同一个 step 中哪个 rank 最慢，慢在哪里。

3.3 常见 Trace 信号与解释

Trace 现象可能根因下一步
GPU 上出现大段空白CPU launch 慢、DataLoader 慢、同步阻塞、H2D copy 阻塞看 CPU thread、CUDA API、Memcpy、DataLoader worker
cudaMalloc 出现在 step 内动态 shape、临时 tensor、未预分配静态 shape、memory pool、CUDA Graph
cudaStreamSynchronize 很多隐式同步、日志取 tensor.item()、跨 stream 依赖搜索代码中的 item/synchronize/print tensor
NCCL AllReduce 排在 backward 之后没有 overlap、bucket 配置不合适、grad ready 时间晚看 bucket、stream、Megatron overlap 开关
某 rank NCCL 时间明显长网络慢、rank mapping 错、straggler查 nvidia-smi topo、IB counter、DCGM
实践建议：每次只采 5～20 个稳定 step。trace 太长会很难读，也会引入 profiler overhead。

4. Nsight Compute / Kernel 分析

Nsight Compute 用来看单个 CUDA kernel 为什么慢。它回答的是“这个 kernel 被什么限制住”。

4.1 Kernel 分类

Roofline 思维：先判断 kernel 是 memory bound 还是 compute bound。不同瓶颈对应完全不同的优化手段。

4.2 必看指标

指标怎么看优化方向
SM ThroughputSM 是否忙提高并行度、减少 stall、优化 occupancy
Memory ThroughputHBM/L2 是否接近峰值coalescing、减少访存、fusion、shared memory
Tensor Core UtilizationGEMM 是否用到 Tensor Coreshape 对齐、使用 FP16/BF16/FP8、CUTLASS/cuBLASLt
Warp Stall Long Scoreboard等待 global memory 结果prefetch、tiling、提高数据复用、cp.async
Warp Stall Barrier等待同步减少 __syncthreads、warp-level primitive
Register / thread寄存器过多会降低 occupancy减少 live range、拆 kernel、launch_bounds
Shared Memory Bank Conflictshared load/store 被 bank conflict 放大padding、调整布局、向量化访问

ncu --set full \
  --target-processes all \

  -o reports/layernorm_ncu \
  python repro_layernorm.py

# 只看关键 section，速度更快
ncu --section SpeedOfLight --section MemoryWorkloadAnalysis --section SchedulerStats python repro.py

5. CUDA Kernel 优化

Kernel 优化的核心不是“堆技巧”，而是针对瓶颈选策略。

5.1 内存层级示意

5.2 Memory Bound Kernel：LayerNorm / Softmax / Elementwise

这类 kernel 的优化目标是减少 HBM 访问次数，提升访存合并和数据复用。

问题Trace / NCU 信号优化手段
多次读写 HBMMemory Throughput 高，SM Throughput 低fuse bias + gelu + dropout；fuse residual + layernorm
访存不连续Global Load Efficiency 低coalesced access，向量化 load：float4 / half2
shared memory bank conflictShared replay / bank conflict 高padding，换 layout，warp-level reduce
同步过多Stall Barrier 高减少 block-wide sync，使用 warp shuffle

5.3 Compute Bound Kernel：GEMM / MLP

这类 kernel 目标是吃满 Tensor Core。

  • 矩阵维度尽量对齐 Tensor Core tile，例如 8/16/32 的倍数。
  • 使用 BF16/FP16/FP8；确认没有 fallback 到 FP32 CUDA core。
  • 使用 cuBLASLt / CUTLASS / Transformer Engine 的 tuned kernel。
  • 注意 small GEMM：MoE、micro batch 太小、专家切分过细会导致 GEMM 尺寸变小，Tensor Core 利用率下降。

5.4 Kernel Fusion

Transformer 中常见可融合区域：

Linear + Bias
Bias + GELU
Dropout + Residual + LayerNorm
Scale + Mask + Softmax
AdamW update
RMSNorm
Rotary Embedding
判断是否值得融合：如果 nsys 里看到很多 5～30 微秒的小 kernel，且中间有 HBM 往返，fusion 通常有效。如果瓶颈是大 GEMM，fusion 收益有限。

5.5 一个 LayerNorm Kernel 学习项目

  1. 先用 PyTorch 实现 baseline，并采 nsys/ncu。
  2. 写 naive CUDA：每行一个 block，计算 mean/var。
  3. 用 warp reduce 替代 shared memory reduce。
  4. 用 half2/float4 做向量化读写。
  5. 尝试 fuse residual + layernorm。
  6. 对比 PyTorch、Apex、Transformer Engine。

6. Attention / FlashAttention 优化

标准 attention 最大问题是中间矩阵 QK^T 太大，读写 HBM 成本高。FlashAttention 的核心是 tile + online softmax，避免保存完整 attention matrix。

优化重点：tile size、shared memory 复用、寄存器占用、warp specialization、double buffer、cp.async。

Trace 中怎么识别 Attention 瓶颈

现象解释优化
attention kernel 时间随 seq_len 二次增长标准 attention 或 backend 不合适切换 FlashAttention / cuDNN attention，检查 mask/dropout/shape 是否触发 fallback
FlashAttention occupancy 低寄存器/shared memory 过多，tile 不合适调 head_dim、block size，查看 register pressure
Stall Long Scoreboard 高等待 HBM/L2提高 K/V tile 复用，使用 prefetch / cp.async
小 batch 长序列效率差并行度不足sequence parallel/context parallel，调整 batch/seq 切分

7.2 NCCL 排查步骤

  1. 先确认通信类型：DP、TP、PP、EP 哪一种。
  2. 看通信是否暴露：如果 NCCL 完全在 compute 后面，说明没有 overlap。
  3. 看每个 rank 的 NCCL 时间是否一致：不一致要查 straggler。
  4. 看节点内与跨节点通信：TP 最好放在 NVLink/NVSwitch 内，DP 跨节点更常见。
  5. 查 NCCL log：算法、通道数、网卡选择、GDR 是否启用。

8. 系统与集群优化

8.1 拓扑感知 Rank Mapping

并行维度要映射到正确硬件链路。一般原则：

  • TP 通信频繁且量大，优先放节点内 NVLink/NVSwitch。
  • PP 需要 P2P，尽量让相邻 stage 在高速链路或同节点。
  • DP 可跨节点，但要确保 IB 带宽和 GDR 正常。
  • MoE EP 的 all-to-all 对网络很敏感，必须关注跨节点 expert 分布。

8.2 NUMA / CPU Affinity

常见问题：GPU 在 Socket0 下，但训练进程或 DataLoader worker 被调度到 Socket1，导致 PCIe/内存访问绕路。

# 查看 GPU / NIC / CPU 拓扑
nvidia-smi topo -m
lstopo
numactl --hardware

# 绑定 CPU / NUMA 示例
numactl --cpunodebind=0 --membind=0 python train.py
taskset -c 0-63 python train.py

8.4 系统层常见坑

  • GPU 降频：功耗、温度、ECC 错误导致性能波动。
  • PCIe ACS/IOMMU 设置影响 P2P/GDR。
  • 容器内没有正确挂载 RDMA device。
  • 多租户网络拥塞导致 NCCL 长尾。
  • 日志/监控过重，step 内频繁 tensor.item() 造成同步。

9. 数据与 Checkpoint IO

9.1 DataLoader 瓶颈

Trace 中如果 GPU 空洞与 CPU DataLoader 时间吻合，优先优化数据路径。

  • 使用 mmap / streaming dataset，避免大量小文件随机读。
  • 预 tokenization，训练时不要做重 CPU 文本处理。
  • 增加 prefetch，pin memory，异步 H2D copy。
  • 检查 worker 数量与 CPU 核数、NUMA、磁盘带宽。
  • 对多节点训练，避免所有 rank 读取同一个远程存储热点。

9.2 Checkpoint IO

大模型 checkpoint 会造成 IO 风暴。优化目标是异步、分片、限流、可恢复。

11. 排查清单

训练慢：先问这 10 个问题

  1. step time 是稳定慢，还是偶发长尾？
  2. GPU timeline 有没有空洞？
  3. CPU 线程有没有长时间阻塞？
  4. CUDA API 里有没有 synchronize / malloc / memcpy？
  5. NCCL 是否暴露在 compute 之外？
  6. 慢的是所有 rank，还是某几个 rank？
  7. DataLoader 是否跑满 CPU/磁盘？
  8. Kernel 是 memory bound 还是 compute bound？
  9. GPU 是否降频、温度/功耗/ECC 是否异常？
  10. 拓扑是否合理：TP/PP/DP/EP 是否映射到正确链路？

优化优先级

先解决端到端大瓶颈：GPU idle、DataLoader、NCCL exposed、straggler。只有当 trace 证明单个 kernel 是主要瓶颈时，才进入 CUDA kernel 深度优化。
