# 00_整体架构与设计理念

## 1. 目标论证

**为什么需要 picotron？**

训练大语言模型(Llama-2-70B/Claude-3系列)面临核心挑战：
- 单GPU显存无法容纳完整的模型参数
- 训练序列长度超过内存限制(100K~1M tokens)
- 需要最大化分布式硬件利用率

现有方案(Megatron-LM、DeepSpeed、Nanotron)功能齐全但代码复杂度高(数万行)，不利于教学和理解核心原理。

**picotron 的教育价值定位：**
| 维度 | picotron | Megatron-LM | Nanotron |
|-----|----------|-------------|----------|
| 代码量 | <2,000行 | ~50,000行 | ~20,000行 |
| 学习曲线 | 陡峭度低 | 陡峭度高 | 中等 |
| 功能覆盖 | 4D并行核心 | 全功能生产级 | 生产级 |
| 最佳用途 | 原理教学 | 工业部署 | 工业部署 |

## 2. 工作假设

**适用场景：**
- 显存受限的单节点/多节点训练
- 需要支持超长上下文(>32K)的场景
- 分布式训练算法学习和研究

**依赖条件：**
- PyTorch 2.1+ with CUDA/NCCL
- CUDA Compute Capability >= 7.0
- 统一硬件配置(GPU型号一致)

**非目标场景：**
- 异构硬件训练
- 模型推理服务
- CPU-only训练(性能非最优)

### 3.2 极简实现原则

| 文件 | 行数 | 核心职责 |
|-----|------|----------|
| `train.py` | ~280 | 训练主循环 |
| `model.py` | ~300 | Llama模型定义 |
| `process_group_manager.py` | ~70 | 4D进程组管理 |
| `tensor_parallel.py` | ~190 | TP实现 |
| `pipeline_parallel.py` | ~220 | PP及调度器 |
| `data_parallel.py` | ~170 | DP带bucket优化 |
| `context_parallel.py` | ~200 | Ring Attention |
| `checkpoint.py` | ~290 | Lazy初始化与存储 |

**工程简化点：**
1. **单一架构支持** - 仅实现 LLaMA 架构，移除多模型适配层
2. **硬编码优化** - 核心融合算子(Fused Adam、RMSNorm)简化配置
3. **函数式调度** - PP引擎用纯函数而非复杂状态机实现

## 4. 故障模式

| 问题 | 可能原因 | 解决方案 |
|-----|---------|---------|
| `World size mismatch` | 配置的总并行度与实际进程数不符 | 检查 `tp×cp×pp×dp == nproc_per_node×nnodes` |
| 4D网格计算错误 | CP维度未正确初始化 | 确保 CP size >=1, 即使不使用CP |
| 内存持续增长 | Pipeline激活未释放 | 检查 `deallocate_output_tensor` 功能是否开启 |
| 梯度不同步 | DP与PP协作问题 | 确保在正确时机设置 `require_backward_grad_sync` |
